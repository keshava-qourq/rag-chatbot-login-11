# RAG Chatbot with Login, Chat History and Gemini

Build a RAG chatbot. Users sign up and log in, upload documents, and ask questions about
them. Answers come only from the chosen document. Every chat is saved, so users can come
back to it later. Use the Google Gemini API (free tier) for embeddings and answers.

## Tech stack
- Frontend: React.
- Backend: Python FastAPI with SQLAlchemy.
- Database: PostgreSQL through DATABASE_URL. When DATABASE_URL is not set, the starter
  project falls back to SQLite, and the app must work on both. So store embeddings as a
  JSON list of numbers, not a Postgres-only vector type.
- Create the tables at startup (Base.metadata.create_all). No migration tool.

## Backend libraries (declare all of these in requirements.txt)
- google-genai: the Gemini SDK
- pypdf: read PDF files
- python-docx: read DOCX files
- python-multipart: file uploads in FastAPI
- numpy: cosine similarity search
- bcrypt: hash passwords
- PyJWT: login tokens

## Settings (environment variables, never hardcoded)
- DATABASE_URL: optional. SQLite is used when it is not set.
- JWT_SECRET: optional. If it is not set, generate a random one at startup and log a
  warning that users will be logged out on every restart.
- GEMINI_API_KEY: optional. If it is not set, each user pastes their own key after
  logging in. The backend keeps it in memory for that user only. It never stores it in
  the database, logs it, or sends it back.
- GEMINI_CHAT_MODEL, default "gemini-2.5-flash"
- GEMINI_EMBED_MODEL, default "gemini-embedding-001"

## Database tables
- users: id, email (unique), password_hash, created_at
- documents: id, user_id, filename, chunk_count, created_at
- chunks: id, document_id, chunk_index, page (nullable), text, embedding (JSON)
- chats: id, user_id, document_id, title, created_at
- messages: id, chat_id, role ("user" or "assistant"), content, sources (JSON), created_at
Deleting a document deletes its chunks and chats. Deleting a chat deletes its messages.

## Running it

```bash
npm install
npm run dev
```

`npm run build` bundles the app; it does not typecheck. The screens were generated, and a
generated screen that renders correctly can still not satisfy `tsc` -- usually an untyped
`useState({})` that is then read for named fields. Deployment would fail on that, which is
a poor reason not to ship a working prototype.

`npm run typecheck` runs `tsc --noEmit` when you want it, and is worth fixing before this
becomes a codebase anyone maintains.

## Checks and tests

- `npm run lint` / `npm run lint:fix` -- ESLint over the whole app; `lint:fix` applies the
  fixes it can. The platform runs `npm run lint` as a gate during development, so keep it green.
- `npm run test` -- Vitest component tests, beside the components they cover.
- `npm run test:e2e` -- Playwright acceptance tests from the `e2e/` folder beside `src/`.
  `npm run test:e2e:install` fetches the browser first. With `E2E_BASE_URL` set it runs against
  that deployed URL; without it, Playwright builds and serves this app and runs against that.
